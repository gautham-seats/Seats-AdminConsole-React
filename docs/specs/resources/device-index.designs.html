Devices list — five UI/UX structures

Each preview runs inside the real Admin shell (nav bar copied from src/shared/shell/NavBar.tsx) with Scheduler tokens. All five share one data and behaviour script: the same simulated GetDevices contract (search, filters only on Search, server-side sort and paging), the same cascade and battery-clamp rules, and the same dialogs and toasts. Only layout, hierarchy and interaction model change. Data is fake. Use the state switcher above each preview to see every state.

Rules shared by all five

  • Filters apply on Search only. Include inactive, Site, Building, Room and Battery are drafts until Search (or Enter in the search box). An amber “not applied yet” hint appears while the draft differs.
  • Cascade: Site clears Building + Room. Building back-fills Site and clears Room. Room back-fills Building and Site. Options narrow top-down.
  • Battery range: one clamp (0–100, min ≤ max by moving the other bound). Sent only after the user touches it. Hidden with the Battery column, as in legacy.
  • Loading: nothing for 400 ms. Then Tide for the first full-page load, and Gearwork over the existing table for later reloads. Stale responses are ignored.
  • Error ≠ empty: a failed load shows an error with Retry and keeps filters. Empty shows “There are no items to show.”
  • Selection is per page and clears after a reload. Reprocess needs exactly one row. Delete needs one or more.
  • Legacy bugs not copied: one load on mount (no double load), a single clamp, unique header ids, no console logs, and the route gate matches the data gate (Rooms-only users see “No access”, not an empty grid).
  • Long values truncate with an ellipsis and show a keyboard-reachable tooltip. Description and the checkbox column stay sticky, with shadow cues when scrolling sideways.

Proposal (needs approval) — not in any preview

  • Stale heartbeat cue — mark devices with no heartbeat for more than 24 h. Needs a product rule for “stale”.
  • Column visibility and density menu — let admins hide low-priority columns. Needs per-user storage (D-009).
  • Remember page size, sort and filters per user — also blocked on D-009.
  • Relative times (“12 min ago”) with the absolute date in a tooltip.
  • Export completion link in the toast once the async report is ready. Needs a notification hook.
  • Server-side grouping for design 5, so groups cover all pages, not only the loaded page. Needs an API change.

Open questions (product decisions)

  1. Include inactive timing. Legacy reloads the grid the moment the box is ticked (deviceIndexController.js:75-77). The spec and this brief say “apply on Search”. These designs follow the spec. Confirm that the change in behaviour is wanted.
  2. Removing a filter chip reloads straight away (clearing is an explicit action). Should it only reset the draft and wait for Search instead?
  3. Gearwork and Tide don't exist in any repo yet (the shared DelayedLoading is a spinner). They are drawn here as proposals. Approve them as shared loaders, or keep the spinner.
  4. Reprocess date culture. The server parses the date with the user's UI culture (DeviceApiController.cs:279) while the picker is fixed to dd/MM/yyyy. Should React send ISO dates (needs backend), or keep the legacy string?
  5. Success wording. Legacy shows generic “saved” toasts for reprocess and the ReportProcessing resource for export. Can we add resource keys for the calmer wording used here?
  6. Export permission. The view has no gate, and the API has no explicit Devices check on Export. Should the button require Devices + Access (it does here, because the whole page does)?
